** Milestone: v1.0 — GMSD Diataxis Integration

*Shipped:* 2026-03-03
*Phases:* 5 | *Plans:* 10 | *Timeline:* 3 days (2026-02-28 → 2026-03-02)

*** What Was Built
- Diataxis reference framework (=diataxis.org= + =diataxis-condensed.md=) as shared vocabulary for all agents
- 38/38 templates classified by Diataxis quadrant; 7/7 agents tagged with =<diataxis_style>=
- Formal audit document (=diataxis-audit.org=) with gap analysis and MermaidJS distribution chart
- New tutorial and how-to templates filling critical quadrant gaps
- =USER-GUIDE.org= split into =docs/howto.org= and =docs/reference.org=; README.org restructured as tutorial hub
- All 18 =references/= files classified with Diataxis metadata
- Retroactive VERIFICATION.org for Phases 1–2 closing procedural gaps

*** What Worked
- *Pipeline architecture:* Phases formed a clean dependency chain (framework → classify → fill gaps → internal docs → verify). Each phase produced artifacts consumed by the next — easy to verify integration
- *Dual-document pattern:* Authoritative .org + condensed .md for agent consumption proved effective and reusable (matches existing org-styleguide pattern)
- *Wave-based parallelism in Phase 2:* 3 plans across 2 waves; classification plans (02-01, 02-02) ran in Wave 1, audit (02-03) ran in Wave 2 after classification was complete
- *Summary-extract tool:* When fields matched, instant structured data from SUMMARYs
- *Integration checker:* Caught the diataxis-audit.org 20-byte cosmetic drift between repo and installed copies

*** What Was Inefficient
- *summary-extract tool* didn't parse some org property drawer fields (=provides=, =one_liner=, =requirements-completed= with hyphens) — required manual grep fallback
- *Phase 5 (Retroactive Verification)* was a corrective phase that wouldn't have been needed if the verification workflow step had existed from Phase 1. Phases 1–2 predate the verification workflow, so this was expected but still a cost
- *STATE.org progress counters* were stale (showed 3/5 completed phases, 6 plans when 10 exist) — the CLI updated =last_updated= but not the body content
- *Roadmap analyze tool* returned empty results, requiring manual verification of phase completeness

*** Patterns Established
- *=:diataxis_primary:= property drawer:* Standard metadata for Diataxis classification on all templates
- *=<diataxis_style>= tag pattern:* Place after =</org_style>=, 15-22 lines, include anti-patterns, reference condensed doc
- *Single-quadrant agents* (4: roadmapper, phase-researcher, codebase-mapper, verifier) → Reference rules
- *Multi-quadrant agents* (3: executor, planner, project-researcher) → per-output-type sub-sections
- *=:re_verification: true=* flag for VERIFICATION.org files applied retroactively
- *Bookend structure for tutorials:* "What you'll learn" / "What you learned"

*** Key Lessons
1. *Build verification into the workflow from the start.* Phase 5 existed solely to backfill missing VERIFICATION.org files for Phases 1–2. Going forward, every execute-phase should produce a VERIFICATION.org
2. *Audit → Fill → Re-audit is a proven gap-closure loop.* The Phase 2 audit drove Phase 3 work; Phase 3 updated the audit; the milestone re-audit confirmed closure. This pattern can be reused
3. *Classification metadata is cheap, directory restructuring is expensive.* The decision to classify in-place rather than reorganize directories was validated — 38 files gained metadata with zero user-facing disruption

*** Architecture Retrospective

*Architectural Decisions Made:*
- *Diataxis as framework:* ✓ Good — maps cleanly to the two-layer system (GMSD internal + user project deliverables)
- *Classify not restructure:* ✓ Good — invisible to users, metadata-driven, no migration cost
- *Dual-document reference:* ✓ Good — reuses established pattern from org-styleguide

*Architectural Patterns That Emerged:*
- *Pipeline integration:* Phase outputs → next phase inputs through file-based contracts (no runtime API). Clean and auditable
- *Property-drawer-as-interface:* =:diataxis_primary:= acts as a machine-readable interface that the audit document consumes. This is an accidental but good architecture pattern

*Architecture Lessons:*
- *Boundary placement:* Phase boundaries aligned perfectly with architectural boundaries. Each phase owned a clear domain. No cross-boundary reaching needed
- *Integration points:* All file-based, all schema-consistent. The =diataxis-audit.org= as single source of truth for coverage state was the key integration contract
- *Quality attributes:* Maintainability drove decisions — classification metadata over restructuring; retroactive verification over accepting procedural gaps

*ADR Candidates:*
- "Dual-document reference as GMSD convention" — deferred (awaiting hat-trick: 3 instances)
- "Reference dominance as intentional architecture" — deferred
- "Property drawer as classification interface" — candidate for future ADR if pattern grows

*** Cost Observations
- Model mix: predominantly Sonnet for agents, Opus for orchestration
- Sessions: ~4 sessions across 3 days
- Notable: Phase 3 (gap filling) was fastest at 6min total — well-scoped phases with clear audit-driven specs execute quickly

** Milestone: v1.1 — MermaidJS ASCII Integration

*Shipped:* 2026-03-04
*Phases:* 1 | *Plans:* 3 | *Timeline:* 1 day (2026-03-04)

*** What Was Built
- =render-mermaid.cjs= Facade over beautiful-mermaid with 120-column width enforcement and paddingX fallback [2,1,0]
- All 9 ob-mermaid blocks across 5 template files replaced with pre-rendered ASCII; Mermaid source preserved in =:exports none= blocks
- Both styleguides (=org-styleguide.md= and =org-styleguide-full.org=) document EXAMPLE + =:exports none= convention
- Diataxis reference diagrams (classification tree + distribution bar chart) rendered as ASCII
- Tech debt from audit resolved: EXAMPLE case standardized, VERIFICATION.org corrected, REQUIREMENTS.org created

*** What Worked
- *Facade pattern:* Single file (render-mermaid.cjs) encapsulates all beautiful-mermaid interaction. Clean boundary — no other code touches the library directly
- *Pre-rendered static content:* Diagrams rendered at authoring time, committed as static text. Agents read ASCII directly — zero runtime dependencies
- *Source preservation:* =:exports none= blocks keep Mermaid source available for re-rendering without cluttering agent-visible content
- *Plan 02 batch rendering:* Rendered all 9 diagrams in one session using the CLI, then copy-pasted results into templates. Efficient batch workflow
- *Tech debt closure before milestone completion:* Running the audit then immediately addressing tech debt meant the milestone archived cleanly

*** What Was Inefficient
- *Template sync gap:* Plan 03 execution synced references but missed 4 of 5 template files. The verification caught it, but the gap persisted until tech debt closure. Root cause: sync step was manual (=cp= commands) with no automated diff check
- *EXAMPLE block case divergence:* The two styleguides prescribed different cases from the start (v0.x era). This wasn't caught until the v1.1 audit. Earlier styleguide reconciliation would have prevented 20-file cleanup
- *Audit file naming:* Created as =v1.0-MILESTONE-AUDIT.org= because the version assignment happened mid-flow. Renamed to v1.1 during archival — minor friction

*** Patterns Established
- *EXAMPLE + :exports none:* Canonical pattern for all MermaidJS diagrams in org-mode templates
- *paddingX fallback [2,1,0]:* Width enforcement strategy for beautiful-mermaid rendering
- *Lowercase =#+begin_example=:* Standardized case for all org-mode EXAMPLE blocks project-wide
- *Description list syntax (=Term :: explanation=):* Replaces bold-dash pattern in org-mode documents

*** Key Lessons
1. *Automate sync steps.* Manual =cp= commands are error-prone — the 4-file sync gap was the only verification failure. A sync script or diff check would prevent this
2. *Reconcile styleguide sources early.* Two styleguide versions with different prescriptions create silent divergence that compounds over time
3. *Tech debt closure is cheap when done immediately.* The 3 tech debt items took ~10 minutes to resolve at milestone boundary — would have been much harder to track down later

*** Architecture Retrospective

*Architectural Decisions Made:*
- *Facade pattern for ESM-only package:* ✓ Good — dynamic =import()= contained to one file; CJS project needs no migration
- *Pre-rendered static content:* ✓ Good — zero runtime dependencies, agents see ready-to-use ASCII, source preserved for re-rendering
- *EXAMPLE + :exports none convention:* ✓ Good — clean separation of rendered output and renderable source

*Architectural Patterns That Emerged:*
- *Render-once, read-many:* Diagrams are rendered during authoring and never re-rendered unless explicitly requested. This is a content architecture pattern — static generation at write time, not read time
- *Dual-content blocks:* The EXAMPLE+:exports none pairing is a form of progressive disclosure — agents and readers see ASCII; authors see both ASCII and source

*Architecture Lessons:*
- *Boundary placement:* The Facade boundary at render-mermaid.cjs was exactly right. All ESM/CJS complexity is hidden behind one async function
- *Integration points:* File copy (source → installed) remains the weakest integration point. No automated validation exists for this connection
- *Quality attributes:* Portability drove the choice of pre-rendered ASCII over runtime rendering. Agents and terminals don't need Mermaid tooling installed

*ADR Candidates:*
- ADR-002 already captures the MermaidJS ASCII rendering decision (=accepted=)
- "Render-once, read-many as content architecture" — potential future ADR if pattern extends beyond diagrams

*** Cost Observations
- Model mix: Sonnet for executor agents, Opus for orchestration
- Sessions: 2 sessions in 1 day (execution + tech debt/audit/completion)
- Notable: Single-phase milestone with tight scope executed quickly (~35min for 3 plans)

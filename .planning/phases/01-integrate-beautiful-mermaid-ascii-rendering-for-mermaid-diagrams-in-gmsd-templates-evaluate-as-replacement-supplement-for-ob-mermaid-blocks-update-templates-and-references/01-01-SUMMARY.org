** Decisions Made

- Used dynamic ~import()~ inside the async function body to load ~beautiful-mermaid~, which is ESM-only (~"type": "module"~ in its ~package.json~, no CJS export). This avoids converting the entire project to ESM while keeping the render script in ~.cjs~ format consistent with the project's existing CJS modules.
- ~renderWithinWidth~ is async as a consequence of the dynamic import. All callers must ~await~ the result. This is documented in the module JSDoc.
- ~useAscii: false~ defaults to Unicode box-drawing characters (┌─┐│└┘►). The option name is inverted from expectations: ~false~ means "use Unicode", not "use ASCII". Documented in the script to prevent future confusion.

** Deviations from Plan

*** Auto-fixed Issues

*1. [Rule 1 - Bug] Replaced synchronous ~require()~ with dynamic ~import()~ for ESM-only package*

- *Found during:* Task 1 (render script creation and verification)
- *Issue:* ~beautiful-mermaid~ uses ~"type": "module"~ in its ~package.json~ and exposes only an ESM export (~import~) in its exports map. ~require('beautiful-mermaid')~ from a CJS module throws ~ERR_PACKAGE_PATH_NOT_EXPORTED~ at runtime. The plan assumed CJS ~require()~ would work.
- *Fix:* Changed ~renderWithinWidth~ to an ~async~ function using ~await import('beautiful-mermaid')~ inside the function body. This is a standard pattern for using ESM packages from CJS contexts in Node.js.
- *Files modified:* ~get-my-shit-done/bin/render-mermaid.cjs~
- *Verification:* Script renders flowchart, sequenceDiagram, and stateDiagram-v2 to stdout. All 6 unit tests pass. Exit code 0.
- *Committed in:* ~9dc4caa~ (Task 1 commit)
- *Architectural note:* The ESM-CJS boundary is a contract violation at the module system level. The plan assumed beautiful-mermaid exported a CJS-compatible interface; it does not. The Facade pattern chosen for this script correctly isolates this boundary: if beautiful-mermaid later adds a CJS export or the project migrates to ESM, only this file changes.

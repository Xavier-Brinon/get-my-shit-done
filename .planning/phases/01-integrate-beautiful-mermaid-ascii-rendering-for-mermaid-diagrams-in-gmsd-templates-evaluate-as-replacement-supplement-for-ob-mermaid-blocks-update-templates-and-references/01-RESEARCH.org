** Summary

=beautiful-mermaid= (v1.1.3) is a pure TypeScript npm package that renders
Mermaid diagram source into ASCII/Unicode art via =renderMermaidASCII()=.
It has no CLI binary — usage is programmatic only. This means the rendering
integration point is a Node.js script run at authoring time, not at agent
inference time. The package supports 6 diagram types: flowcharts, state
diagrams, sequence diagrams, class diagrams, ER diagrams, and XY charts.

The audit of actual ob-mermaid usage in templates reveals: 5 templates use
ob-mermaid blocks covering 3 diagram types (flowchart, sequenceDiagram,
stateDiagram-v2). No agents currently embed Mermaid syntax inside
=<architecture_learning>= blocks — the "9 agents" scope from MEMORY.md refers
to agents whose =<org_style>= tag references the styleguide (which contains
ob-mermaid conventions). The actual update scope is the styleguide files and
the template =#+begin_src mermaid= blocks.

The primary challenge is that =beautiful-mermaid= does not expose a width
parameter — output width is emergent from diagram structure and =paddingX=.
Achieving the 120-column constraint requires adjusting =paddingX= and,
where diagrams still exceed width, simplifying the Mermaid source itself.
The rendering script must be the canonical tool that both validates and
produces all ASCII blocks in the project.

*Primary recommendation:* Write a Node.js render script using
=beautiful-mermaid= ~renderMermaidASCII()~ with tuned =paddingX= that
produces ASCII within 120 columns; replace all 9 =#+begin_src mermaid=
ob-mermaid blocks in templates + 2 ob-mermaid references in
=org-styleguide.md= and 1 in =workflows/org-review.md= in an atomic pass.

*** Pattern 1: Render Script (Facade)

*What:* A Node.js CJS script that accepts Mermaid source on stdin or as a
file argument and outputs the rendered ASCII string to stdout.

*When to use:* Called during template authoring, phase execution, and whenever
a diagram needs rendering. The script is the single integration point.

#+begin_src javascript
// Source: beautiful-mermaid npm package (v1.1.3)
const { renderMermaidASCII } = require('beautiful-mermaid');

const diagram = `flowchart LR
    A[Phase 1] --> B[Phase 2]
    B --> C[Phase 3]`;

const ascii = renderMermaidASCII(diagram, {
  paddingX: 2,
  paddingY: 1,
  useAscii: false  // false = Unicode box-drawing chars (better readability)
});

console.log(ascii);
#+end_src

*** Pattern 3: 120-column width management

*What:* =beautiful-mermaid= does not expose a width parameter. Width emerges
from content and =paddingX=. The workflow is: render with tuned =paddingX=
→ measure output width → simplify diagram if needed → re-render.

#+begin_src javascript
// Source: beautiful-mermaid npm package (v1.1.3)
function renderWithinWidth(diagramSource, maxCols = 120) {
  for (const paddingX of [2, 1, 0]) {
    const ascii = renderMermaidASCII(diagramSource, { paddingX, paddingY: 1 });
    const maxLineWidth = Math.max(...ascii.split('\n').map(l => l.length));
    if (maxLineWidth <= maxCols) return ascii;
  }
  // Still too wide: caller must simplify diagram source
  return null;
}
#+end_src

*** Anti-Patterns to Avoid

- *Keeping ob-mermaid as fallback*: Decision is locked — full replacement.
  Mixed rendering state causes inconsistency in styleguide guidance.
- *Runtime rendering in agents*: Agents produce text; they should not invoke
  =beautiful-mermaid= at inference time. ASCII diagrams are pre-rendered
  static content in templates.
- *Wrapping ASCII in =#+begin_src= blocks with a language tag*: Language-tagged
  src blocks imply code that can be executed. Use =#+BEGIN_EXAMPLE= for
  preformatted ASCII art output.
- *Storing rendered ASCII without source*: Without the preserved Mermaid source,
  diagrams cannot be updated or re-rendered when =beautiful-mermaid= improves.

** Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------+-------------+-------------+-----|
| Mermaid → ASCII conversion | Custom ASCII layout engine | =beautiful-mermaid= | Grid layout, box-drawing, arrow routing are non-trivial; 6 diagram types already supported |
| Width enforcement | Custom truncation logic | =paddingX= tuning + source simplification | Truncation breaks diagram structure; simplification preserves relationships |

*Key insight:* ASCII diagram layout is deceptively complex — box placement,
arrow routing, and label fitting involve constraint solving. =beautiful-mermaid=
handles this for all 6 supported types; custom solutions would need to
reimplement this per diagram type.

** Common Pitfalls

*** Pitfall 1: Output width exceeds 120 columns with default paddingX

*What goes wrong:* =renderMermaidASCII= default =paddingX: 5= produces wide
output. Diagrams with 4+ nodes in a horizontal chain regularly exceed 120
columns.

*Why it happens:* Width is emergent — every node label + border + padding adds
to total width. Default padding is generous for visual aesthetics, not terminal
constraints.

*How to avoid:* Start with =paddingX: 2, paddingY: 1= as the default. Provide
a width-check loop (see Pattern 3). If output still exceeds 120 at =paddingX:
0=, the diagram source must be simplified before rendering.

*Warning signs:* Any diagram with more than 3 nodes in a horizontal sequence
is a candidate for width issues.

*** Pitfall 2: Dual file locations — source and installed copy drift

*What goes wrong:* Templates exist in both
=get-my-shit-done/templates/= (source) and
=~/.claude/get-my-shit-done/templates/= (installed copy). Updating only the
source means the installed copy still contains ob-mermaid blocks.

*Why it happens:* The install script copies source to =~/.claude/= at install
time. Changes to source do not auto-propagate.

*How to avoid:* The atomic update pass must modify *both* locations — source
files and installed copies. Document this as a two-location update in the plan.
Similarly for reference and workflow files.

*** Pitfall 3: =#+begin_details= availability in org-mode

*What goes wrong:* If org-mode version in use does not support
=#+begin_details= / =#+end_details= for foldable blocks, the source-
preservation pattern breaks.

*Why it happens:* =#+begin_details= is an org-mode 9.6+ feature. Earlier
versions only support =:PROPERTIES:= drawers for folding.

*How to avoid:* Verify org-mode version or use a universally supported
alternative for the collapsed Mermaid source block (e.g., a =:COLLAPSED:=
property drawer, or a plain comment block if re-rendering is treated as a
manual step). Marked as Claude's discretion in CONTEXT.org.

*** Pitfall 4: =beautiful-mermaid= has no CLI — not executable directly

*What goes wrong:* Attempting =npx beautiful-mermaid diagram.mmd= fails.
The package has no =bin= entry and no CLI.

*Why it happens:* =beautiful-mermaid= is a library, not a tool. The npm
package metadata confirms =bin: None=.

*How to avoid:* The render script =bin/render-mermaid.cjs= must wrap the API.
Do not document or reference =npx beautiful-mermaid= usage anywhere.

*** Pitfall 5: =useAscii: false= (Unicode) vs =useAscii: true= (plain ASCII)

*What goes wrong:* =useAscii: true= uses only basic ASCII characters (=+=-=|=)
for boxes and arrows. =useAscii: false= (default) uses Unicode box-drawing
characters (=┌─┐│└┘=). The Unicode version is more readable; the ASCII version
is safe for environments that cannot render Unicode.

*Why it happens:* The API option name is inverted from expectations — =useAscii:
false= produces the prettier Unicode output.

*How to avoid:* Default to =useAscii: false= (Unicode box-drawing). The project
targets Emacs and terminals — both render Unicode. Document this in the render
script.

*** Width-constrained render function

#+begin_src javascript
// Source: beautiful-mermaid v1.1.3 API + project constraint (120 cols)
const { renderMermaidASCII } = require('beautiful-mermaid');

function renderWithinWidth(source, maxWidth = 120) {
  const paddingSteps = [2, 1, 0];
  for (const paddingX of paddingSteps) {
    const ascii = renderMermaidASCII(source, {
      useAscii: false,
      paddingX,
      paddingY: 1,
      boxBorderPadding: 1
    });
    const lines = ascii.split('\n');
    const maxLine = Math.max(...lines.map(l => l.length));
    if (maxLine <= maxWidth) {
      return { ascii, paddingX, width: maxLine };
    }
  }
  return null; // Caller must simplify diagram source
}
#+end_src

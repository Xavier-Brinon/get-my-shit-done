** Summary

Phase 3 creates two org-mode template files — =templates/tutorial.org= and
=templates/howto.org= — that fill the critical Tutorial (0 templates) and
low-coverage How-to (1 template) Diataxis quadrants identified in the Phase 2
audit. The domain is documentation authoring, not software engineering: the
"standard stack" is org-mode conventions and Diataxis writing rules, not
libraries or frameworks.

Both templates follow the established meta-template pattern: file-level property
drawer with =:diataxis_primary:=, a =<template>= block containing the skeleton,
a =<good_examples>= block with one worked example, and a =<guidelines>= block
explaining usage. The closest structural ancestor for both is =user-setup.org=,
which demonstrates the step-based pattern — but the Tutorial quadrant demands
steps chosen for understanding, not efficiency, and a warm encouraging tone that
=user-setup.org= does not use.

Upon completion, the Phase 2 audit document (=references/diataxis-audit.org=)
must be updated: the distribution table, the gap analysis section, and the
recommendations section all reference zero tutorial templates and recommend the
creation that Phase 3 delivers.

*Primary recommendation:* Model both templates on =user-setup.org= structure;
differentiate tutorial via tone (warm, bookends) and howto via generic goal
framing (not service-scoped). Apply org-mode comments for guidance text.

*** Pattern 1: Tutorial template structure

The Tutorial quadrant enforces *separation between doing and understanding* —
steps prompt action; rationale is deferred to separate explanation documents.

#+begin_src org
:PROPERTIES:
:diataxis_primary: tutorial
:diataxis_secondary: none
:diataxis_rationale: Reader follows the generated tutorial to learn the GMSD
  workflow by doing — completing a full phase cycle and building confidence.
:END:

#+title: Tutorial
#+startup: indent
#+options: toc:2 num:nil ^:{}

* Tutorial Template

<template>
#+begin_src org
#+title: [Project]: Your First Phase
#+date: [YYYY-MM-DD]
#+startup: indent
#+options: toc:2 num:nil ^:{}

* Your First Phase

# What you'll learn (set expectations up front — Diataxis rule)
By the end of this tutorial you will have:
- Discussed and scoped a real phase for [Project]
- Generated an executable plan
- Completed at least one task from that plan

Prerequisites:
- GMSD installed and configured (see [[file:user-setup.org][User Setup]])
- A project you want to work on

** Step 1: Discuss your first phase

# Tutorial rule: start with a concrete action immediately
Run the discuss-phase command to define your scope...

#+begin_src bash
/gmsd:discuss-phase
#+end_src

...

** What you learned

# Recap bookend (locked decision in CONTEXT.org)
You have now completed one full GMSD cycle...
#+end_src
</template>
#+end_src

Key structural decisions:
- "What you'll learn" at top (bookend 1 — expectations)
- "What you learned" at bottom (bookend 2 — recap)
- =# comment= headers explain each section's Diataxis purpose (invisible on export)
- Steps numbered and action-first (imperative, not descriptive)
- Milestone acknowledgements between major steps ("Great — you've created your first plan!")
- One concrete =good_examples= block showing a fully completed tutorial

The How-to quadrant enforces *goal-first, competence-assumed* structure — no

* How-to Template

<template>
#+begin_src org
#+title: How to [Goal]
#+date: [YYYY-MM-DD]
#+startup: indent
#+options: toc:2 num:nil ^:{}

# State the goal immediately — reader confirms this solves their problem
* How to [Specific Goal]

# Assume competence — no background explanation

** Prerequisites

# List only blockers. Skip anything the reader can infer.
- [Prerequisite 1]
- [Prerequisite 2]

** Steps

1. [Step 1 — imperative verb, concrete action]
2. [Step 2]
   # Inline conditional: If X, substitute Y
3. [Step 3]

** Verification

# What success looks like
#+begin_src bash
[verification command]
#+end_src

Expected output: [what to look for]

** Troubleshooting

# Edge cases only — not background theory
- *[Symptom]*: [Fix]
- *[Symptom]*: [Fix]
#+end_src
</template>
#+end_src

Key structural decisions:
- Goal in =#+title:= and =* heading= (stated twice — How-to rule: confirm scope immediately)
- Prerequisites section short — only blockers, not background
- Numbered steps (not bullets) — direction matters in a procedure
- Inline conditionals (e.g., "If using Docker, substitute X") — no branching paths
- Verification section — reader confirms success without authorial hand-holding
- Troubleshooting section — brief, symptom→fix pattern only

*** Anti-patterns to avoid

- *Mixing quadrants mid-template:* Tutorial steps that explain "why this works"
  should be =# comments= or omitted, not embedded prose. How-to prerequisites
  should not include background theory.
- *Skipping the bookends in the tutorial:* Both "What you'll learn" and "What
  you learned" are locked decisions — they define the tutorial quadrant's
  success-guaranteed structure.
- *Scoping the how-to to GMSD:* The how-to template must be generic — no
  GMSD-specific framing in the skeleton (only in =good_examples=).
- *Using backticks:* All code references use =~code~= or ==verbatim== markup.
  Backticks have no special meaning in org-mode.
- *Missing blank lines before headings:* Every heading must be preceded by one
  blank line. Missing these causes parser ambiguity.

** Don't Hand-Roll

This is a *build vs. buy* decision applied to documentation authoring.

#+CAPTION: Build vs. established convention decisions
| Problem                          | Don't Invent              | Use Instead                          | Why                                           |
|----------------------------------+---------------------------+--------------------------------------+-----------------------------------------------|
| Template guidance text           | Inline prose mixed with   | =# comment= or =#+begin_comment=    | Org-mode's built-in comment syntax is export- |
|                                  | skeleton content          |                                      | invisible; custom markup is not               |
| Diataxis classification metadata | Custom heading or section | =:diataxis_primary:= property drawer | Matches all 36 existing templates; parseable  |
| Step numbering in how-to         | Custom numbering scheme   | Org numbered lists (=1.=, =2.=)     | Org auto-renumbers; standard rendering        |
| Worked examples block            | Separate file or link     | =<good_examples>= block in same file | Established meta-template pattern             |
| Template framing prose           | Custom XML-like tags      | Existing tag vocabulary:              | Already parsed by agent prompts;              |
|                                  |                           | =<template>=, =<guidelines>=         | consistent with all other templates           |

*Key insight:* Every structural choice in a new template that diverges from the
existing 36 templates creates a maintenance inconsistency. The org-styleguide.md,
the property drawer pattern, and the meta-template block vocabulary are already
established — the correct approach is to follow them precisely.

** Common Pitfalls

*** Pitfall 1: Tutorial becomes a how-to

*What goes wrong:* The tutorial skeleton drifts into assuming reader competence —
steps start with "if you want to..." (goal-assumed) rather than "run this command"
(action-first, teacher-led).

*Why it happens:* Authors naturally slide toward efficiency. Tutorials must
resist this: the path is chosen for learning, not for speed.

*How to avoid:* Apply the Diataxis disambiguation test in the =<guidelines>=
block of the template: "Does the reader know what they want before they start?
If yes, they want a how-to. If no, they want this tutorial."

*Warning signs:* Phrases like "when you need to..." or "if your project
requires..." signal how-to framing. Tutorial steps are unconditional.

*** Pitfall 2: How-to accumulates background theory

*What goes wrong:* A Prerequisites section grows into an explanation of why
prerequisites matter. A Troubleshooting section explains root causes instead of
giving fixes.

*Why it happens:* Explanation is naturally attractive to authors who want the
reader to understand, not just act.

*How to avoid:* Every sentence in the how-to template should answer "does this
help the reader reach the goal faster?" — if it explains rather than directs,
remove it or move it to a comment.

*Warning signs:* Any paragraph that begins with "This is because..." or "The
reason we..." belongs in an explanation document, not a how-to.

*** Pitfall 3: Org-mode comment syntax confusion

*What goes wrong:* Template guidance text uses =# text= without a space, or uses
Markdown-style =<!-- comment -->= which is not valid org-mode.

*Why it happens:* Markdown comment habits carry over. The correct org-mode single-
line comment is =# text= (hash, space, text). Without the space, org-mode
treats it differently in some contexts.

*How to avoid:* Use =# comment= for single-line inline guidance, =#+begin_comment=
/ =#+end_comment= for multi-line blocks.

*Warning signs:* Org export includes guidance text that should have been hidden.
Test by checking that export output omits all template guidance.

*** Pitfall 4: Milestone congratulations break how-to tone

*What goes wrong:* The how-to template adopts encouraging language from the
tutorial template. "Great — you've completed Step 3!" is tutorial tone, not
how-to tone.

*Why it happens:* The two templates are developed in the same phase and tone
can bleed between them.

*How to avoid:* Write how-to copy in neutral third-person ("Step 3 installs
the dependency. Continue when the command exits without error."). Reserve warm
tone exclusively for the tutorial template.

*** Pitfall 5: Audit update misses the MermaidJS chart

*What goes wrong:* The distribution table is updated but the pie chart =#+begin_src
mermaid= block still shows old counts.

*Why it happens:* The chart is visually separate from the table and easy to miss
on a targeted edit.

*How to avoid:* Include audit update as a single task that explicitly lists all
three update targets: distribution table, gap analysis section, and MermaidJS
chart.
